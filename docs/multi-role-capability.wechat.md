# 跟 Agent 聊着聊着，团队就长大了：ArchGraph 的多角色能力到底怎么用

很多人问过我同一个问题：**ArchGraph 的"多角色"到底是个什么？它真的有用吗？**

讲概念之前，我先说一件刚发生在我们自己身上的事。

这篇文章本身，就是被 ArchGraph 的"多角色"能力产出来的：有人负责写稿，有人（"媒体艺术家"这个角色）负责配图。而这支"团队"，是在开发过程中**通过和 Agent 对话，一个一个角色长出来的**。

所以这篇文章不讲虚的，就用 ArchGraph 自己的开发经历，把"多角色"这件事从头到尾讲清楚，并且告诉你每一步怎么操作，照着做就行。

---

## 一、先看结果：我们的"开发团队"长什么样

打开 ArchGraph 项目的意图图谱，在 `AgentOrganization` 下挂着四个团队视图，其中一个是「开发团队」(DevelopmentTeam)：

- **产品经理**（xiaoniu 担任）：梳理用户意图、整理用户场景和用户故事；
- **系统设计师**（caoyang 担任）：基于需求做方案设计；
- **规划专家**（tanwen 担任）：做技术先进性分析，发现问题就反馈给设计师；
- **系统架构师**（laodong 担任）：做架构分析，确保符合 SOLID、安全性、性能；
- **Developer**（Xiaoming 担任）：负责代码开发和自测；
- **Reviewer**（adam 担任）：对代码做架构和安全性检视；
- **验证测试工程师**（chenlin 担任）：负责最终验证测试。

这不是 PPT 上画着好看的流程，这些角色的职责、技能、协作关系，全部**结构化成一张图**，每个角色背后站着一个真实的 Agent。

![我们的 Agent 团队：中央是协作图谱，周围是各司其职的角色](diagrams/multi-role-banner.png)

关键不是"有七个角色"，而是：**这些角色不是一次性设计出来的，而是开发过程中通过对话，一个接一个加进去的。**

最初只有"产品经理 → 系统设计师 → Developer"这条线。后来发现代码写完没人把关，就加了 **Reviewer**；再后来发现需要验证，加了 **验证测试工程师**；再后来发现方案可能不够先进，加了 **规划专家** 和 **系统架构师**。

每次加角色，都是一次对话。这就是 ArchGraph 多角色能力的核心用法。

## 二、多角色能力到底解决了什么问题

单 Agent 干活，最大的问题是**"一个人活成了整个团队"**：

- 它又要理解需求、又要设计、又要写代码、又要自测、又要自查——角色混乱，**职责边界模糊**；
- 它的系统提示词（prompt）越长越乱，改一处牵一发动全身，**行为不可控**；
- 它做完说"做完了"，但**没有独立的角色来验收**，自说自话；
- 换一个 Agent 接着干，之前沉淀的角色经验**全部丢失**。

多角色能力的本质，是**把"一个全能的 Agent"拆成"一支各司其职的 Agent 团队"**：

- 每个角色有**明确的职责**（谁来定？ArchGraph 里每个角色都有 description，这就是它的职责定义）；
- 每个角色有**明确的能力**（通过 Skill 挂载）；
- 每个角色之间有**明确的协作关系**（谁触发谁、谁给谁交付）。

职责、能力、协作，这三样就是多角色能力的全部。ArchGraph 把这三样都做成了**可结构化的图**，于是：

- 团队是**可见的**——打开图谱就能看到谁在干什么；
- 团队是**可生长的**——缺什么角色，加一个就行；
- 团队是**有记忆的**——每个角色挂着自己的长期记忆，换会话也不忘。

## 三、怎么加一个新角色？照着这六步做

接下来是重头戏：**具体怎么操作，才能让 Agent 组织长出新的角色。** 我拿最近一次真实操作——给团队加一个「媒体艺术家」——当例子。

### 第 1 步：向 Agent 提出需求（用自然语言就行）

你不用写任何配置文件。直接在对话里告诉 Agent：

> "我们发布文章需要配图，需要一个负责图片视频生成的角色。"

这就是全部"操作"。剩下的，Agent 会自己去图谱里完成。

### 第 2 步：Agent 创建"角色本体"和"职责"

Agent 收到需求后，会在意图图谱里创建两个元素：

- **Business Actor**（角色本体）：比如「媒体艺术家」。这是有身份的 Agent，挂长期记忆。
- **Business Role**（角色类型）：比如「图片视频生成」。这是职责描述。

其中 Business Role 的 `description` 就是职责定义，会被当成这个角色的系统提示词。比如「图片视频生成」的职责写的是：

> 负责将创作需求（主题、风格、用途、数量、尺寸）转化为可交付的图片/视频。包含需求解析与画面设计、调用图像生成模型产出草稿、使用视觉模型验收并迭代、输出最终图片文件。

写清楚"它负责什么、包含哪些工作、产出什么"，职责就定住了。

### 第 3 步：把角色本体指派给职责（Assignment）

通过一条 **Assignment** 关系，把「媒体艺术家」指派给「图片视频生成」这个职责：

```
媒体艺术家 --(Assignment)--> 图片视频生成
```

这一句的意思是：这个 Agent 就是干这个活的。

### 第 4 步：给角色挂能力（Skill）

光有职责还不够，得让它真的会干活。ArchGraph 里把"能力"建模为 **Skill** 元素，再用 **Association** 关系挂到角色上：

```
图片视频生成 --(Association)--> dashscope-media-generator
图片视频生成 --(Association)--> qwen3-vl-visual-inspection
```

每一个 Skill 都是一个可以复用的"能力包"，里面有完整的操作说明。角色领到任务后，会**沿着图谱自动找到这些 Skill 并加载**——这就是 ArchGraph 的"自武装"：不用把技能写死在 prompt 里。

### 第 5 步：定义和其他角色的协作关系

新角色不是孤岛。它和团队里其他角色怎么配合，也要画进图里。

ArchGraph 用 ArchiMate 的关系类型表达协作。开发团队里就是一组 **Triggering**（触发）关系：

```
产品经理 --(Triggering)--> 系统设计师
系统设计师 --(Triggering)--> Developer
Developer --(Triggering)--> Reviewer
Developer --(Triggering)--> 验证测试工程师
系统设计师 --(Triggering)--> 规划专家
系统设计师 --(Triggering)--> 系统架构师
```

你可以读成一句大白话：**产品经理定完需求，就触发系统设计师去设计；设计师设计完，触发 Developer 去开发；Developer 写完，触发 Reviewer 去检视、触发验证测试工程师去验证。**

![协作流水线：任务沿着角色间的触发关系一站站往下传](diagrams/multi-role-pipeline.png)

协作关系画在图上，Agent 之间就知道谁给谁交付、什么时候该谁出场了。

### 第 6 步：把新角色挂进团队视图，并加验收用例

每个角色都要放进对应的团队视图（View）里，这样整个团队在图上才是完整的一块。

同时，ArchGraph 的硬性要求是**每个架构元素都要有可执行的验收用例**（GIVEN-WHEN-THEN 格式）。比如媒体艺术家的验收用例是：

> GIVEN 意图图谱已登记 AgentOrganization 团队；WHEN 查找专门负责图片视频生成的 Business Actor；THEN 图谱中存在全局唯一 name 为「媒体艺术家」的 Business Actor，挂载于 AgentOrganization，有非空 description，并通过 Assignment 关系指派给「图片视频生成」Business Role，三者均包含于「媒体创作团队」视图。

这个用例不是写给人看的文档，是**可以直接跑起来的测试**（`node --test`）。新角色加得对不对，机器说了算。

## 四、加完角色之后：它怎么被调用

角色加进图谱，只是"上了编制"。真正干活的时候，流程是这样的：

1. 人类或者主 Agent 发起任务；
2. 按协作关系，任务从"产品经理"开始流转；
3. 每个角色在自己的职责范围内干活，通过 Skill 加载能力；
4. 干完活，交付给协作关系里下一个角色；
5. 最后验收用例自动回归，全绿才算交付完成。

你在旁边看着图谱，就能实时知道：**现在活走到哪个角色手上了，它用了什么技能，下一步会触发谁。**

这才是"多角色"和"装了几个 Agent 在一起"的区别——后者是几个黑盒拼凑，前者是一张**可观察、可约束、可纠偏的施工图**。

## 五、这套能力是怎么长出来的（我们的真实轨迹）

回头看看 ArchGraph 自己的 AgentOrganization，它长的每一步都留在了图谱和 git 记录里：

- 最初：一支 7 角色的软件开发团队（DevelopmentTeam）；
- 然后：发布文章需要人管，加了「公众号发布员」（WeChat 发布团队）；
- 再然后：文章需要配图，加了「媒体艺术家」（媒体创作团队）；
- 每个团队一个子视图，挂在 `AgentOrganization` 下。

整个过程**没有一个角色是提前设计好的**，全部是"遇到问题 → 对话 → 加角色"长出来的。而因为每一步都记录在案，团队是怎么长大的，任何人都能回放。

---

## 六、你说"照着做"，到底照着什么做

最后总结成一张操作清单，你在自己的 ArchGraph 项目里照着做就行：

| 步骤 | 做什么 | 在图谱里对应什么 |
| --- | --- | --- |
| 1 | 向 Agent 提需求（自然语言） | 无需操作 |
| 2 | 让 Agent 创建角色 | Business Actor + Business Role |
| 3 | 指派职责 | Assignment 关系 |
| 4 | 挂能力 | Skill + Association 关系 |
| 5 | 定协作 | Triggering / Association 关系 |
| 6 | 归队 + 验收 | 加入 View + 挂可执行验收用例 |
| 7 | 提交留证 | git commit + 把 commit id 回登记到元素上 |

记住一句话：**在 ArchGraph 里，"加一个角色"不是改配置，而是画图。而画图这件事，你说一句话，Agent 就帮你画完了。**

---

ArchGraph 的多角色能力，最后落到一句话：**它让你的 Agent 团队像真实的组织一样，可以一边干活、一边长大，而且每一步都有据可查。**

你不需要一次性设计出完美的团队。从一条最简单的流水线开始，缺什么角色，就聊着加什么角色——就像我们做的这样。
