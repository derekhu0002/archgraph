Agent Modeling Language (AML) v0.1

Status Working Draft Version v0.1 Published 2026-08-17 Editor ArchGraph Metamodel ArchiMate 3.2 (AML extends it) Graph schema .argo/schema/SystemArchitecture.schema.json

Status of This Document: This is the v0.1 Working Draft of AML and is under continuous evolution; its contents may change before a formal release. Readers can track the latest version in the ArchGraph repository.

Abstract

This specification defines the Agent Modeling Language (AML) — a knowledge-graph based modeling language for agent behavior. AML is an extension of ArchiMate 3.2: it extends its vocabulary (new element types) and syntax (new structural conventions), and defines how standard ArchiMate elements are used to model agents. AML targets the modeling and standardization of agentic engineering harnesses, serving as the contract between upstream consumers and downstream vendors.

1Scope and Extensions

AML does not modify the existing element and relationship definitions of ArchiMate 3.2; it only extends at the following layers:

Extension layerContentStandard ArchiMate 3.2?
New element typesSkill, RuleNo, AML extension (layer: Other, aspect: Agent)
New structural conventionstestcases, attributes, subdiagram_views, parentNo, AML extension
AML profile for standard elementsAssigns agent semantics to Work Package, Business Actor, etc.The elements are standard; the semantic conventions are AML additions
This document describes only the extension parts. For definitions of existing ArchiMate 3.2 elements and relationships, see .argo/schema/archimate3.2.pdf.

1.1 Interpretation Loop

  • Program text: the elements, relationships and views in design/KG/SystemArchitecture.json.
  • Interpreter: the agent reads the graph through ARGO MCP (getIntentElementContext / semantic query) and "arms itself" before executing the task.

2Extended Elements

2.1 Skill (skill module)

  • Semantics: a skill module the agent can load.
  • Materialization: .github/skills/<name>/SKILL.md (one Skill element maps to one SKILL.md).
  • Usage: Work Package --Association--> Skill means the task requires the skill; after taking the task, the agent reads the corresponding SKILL.md to "arm itself".
  • Example: element 1319 optimize-web-layout-style → .github/skills/optimize-web-layout-style/SKILL.md.

2.2 Rule (rule module)

  • Semantics: a reusable rule module.
  • Materialization: .github/<name>.instructions.md (one Rule element maps to one instructions file).
  • Usage: Work Package --Association--> Rule means the task must follow the rule; global rules materialize to .github/copilot-instructions.md.
  • Example: element 1320 kglibrary-info-format → .github/kglibrary.instructions.md.

2.3 Distinguishing Skill / Rule from standard elements

ConceptStandard/ExtensionMaterialization target
Capability (standard)Abstract capability, not directly materialized—
Skill (extension)Loadable skill module.github/skills/<name>/SKILL.md
Principle (standard)Global constraintglobal *.instructions.md
Rule (extension)Reusable rule module.github/<name>.instructions.md
Constraint (standard)Local constraint— (attached to the associated Task/Process)

The three levels of constraints:

  • Principle (global): always applies to all tasks, e.g. "find the architecture element before modifying anything".
  • Rule (rule module): a reusable rule, materialized as .github/*.instructions.md.
  • Constraint (local): constrains only the Task / Process it Associations to.

3Extended Structures

3.1 testcases (acceptance assertions)

testcases is AML's assertion mechanism, mounted on elements; standard ArchiMate has no counterpart. Each case must:

  1. GIVEN-WHEN-THEN format: description describes the specification in GIVEN-WHEN-THEN form.
  2. Executable: acceptanceCriteria must be a workspace-relative executable entrypoint (e.g. node --test tests/xxx.test.js).
  3. External verification: verifies observable behavior from outside the element, not the internal implementation.

Example:

{
  "name": "AT-1333-01-language-spec-document",
  "description": "GIVEN the repository keeps a knowledge-graph based memory system; WHEN a reader opens docs/agent-programming-language.md; THEN the document defines the vocabulary, syntax, acceptance assertions and the persistent/runtime boundary.",
  "type": "Acceptance Test",
  "Input": "Open docs/agent-programming-language.md",
  "acceptanceCriteria": "Run node --test tests/agent-programming-language.test.js: assert the document exists and contains the vocabulary, syntax, testcases, persistence/runtime sections. Pass."
}

3.2 attributes (property container)

A general property container for attaching agent engineering metadata to elements. AML-defined property names:

PropertyPurpose
commitRegisters one commit: value=commit id, description=related file paths (multiple allowed)
statusTask status (e.g. COMPLETED)
verification_focus / external_scope / acceptance_outcomes / design_risksArchitecture intent metadata (suggested by the schema)

3.3 subdiagram_views / parent (structural attachment)

  • parent: the element's parent in the view tree (e.g. a Work Package hangs under a Viewpoint Grouping).
  • subdiagram_views: the element's association with sub-diagram views.

5Persistent Elements vs. Runtime Instances

ArchiMate is a design-time language: it models types/definitions, not runtime instances. AML follows the same boundary:

CategoryIn the graph?Examples
Persistent elements (program text) Yes, long-lived Skill, Rule, Business Actor, Business Role, Capability, Work Package, Business Process, Course of Action, Goal, Constraint, Principle
Runtime instances (program execution) No, only results are written back one session, one execution, one commit
  • Business Actor is a persistent person: it has identity and long-term memory (the memory is the knowledge graph itself), and can take part in many executions.
  • An "agent session" is a runtime instance: it is expressed by one execution of Work Package --Assignment--> Business Actor; results are written back through attributes.commit, without creating new elements.

6Complete Program Example

Example: "update the INDEX homepage according to the README" (Work Package 1332):

sync-homepage-program (Course of Action · Program)
└── Composition ── update-INDEX-homepage-from-README (Work Package · Task)
    ├── Assignment ── web-developer (Business Role)
    ├── Association ── optimize-web-layout-style (Skill)
    ├── Association ── kglibrary-info-format (Rule)
    ├── Composition ── update-architecture-section (Business Process · P1)
    │   ├── Access ── index.html (Artifact)
    │   └── Triggering ── update-howto-section (Business Process · P2)
    ├── Composition ── update-howto-section (Business Process · P2)
    │   └── Access ── index.html (Artifact)
    └── Flow ── updated index.html (Deliverable)
        └── Realization ── homepage-synced-with-README (Goal)

only index.html and tests/website.test.js may be modified (Constraint) ── Association ── update-INDEX-homepage-from-README
find the architecture element before modifying (Principle) ── Influence ── update-INDEX-homepage-from-README

7Compliance and Extension Process

  • Skill / Rule are the only two non-standard elements in the archimateElementType enum, registered in .argo/scripts/archimate32-rules.js (layer: "Other", aspect: "Agent").
  • This specification does not modify SystemArchitecture.schema.json.
  • When a new primitive is needed, evaluate in order: ① whether it maps to a standard ArchiMate element (add a convention); ② whether it can be expressed with attributes; ③ only then extend the archimateElementType enum.
