# ArchGraph 开发者社区 — 架构评审

> 工作包：开发者社区开发交付（2751）
> 评审人：laodong（系统架构师，sessionId 88bdf28a-55eb-48d8-9092-a01ecfb6a681）
> 评审对象：docs/developer-community-design.md

## 1. 结论

**需修改**（架构映射本身成立，但安全边界与下载格式校验缺失，需补充后方可进入实现）。

## 2. 架构分析理由

### 2.1 架构映射合理性

- `GitHub Discussions`（Application Service 2752）通过 `Serving` 关系支撑 `ArchGraph开发者社区`（Application Component 2748），语义正确：应用组件是「协作/能力载体」，由外部应用服务提供实际功能，符合 ArchiMate 的 Serving 语义。
- 移除自研组件 `开发者社区WEB前端`（2749）、`开发者社区后端服务`（2750）及关系 1964，与需求 NF-1「零成本、零运维、不自研社区系统」一致，映射干净、无冗余。
- 保留 2748 作为逻辑组件是必要的：它是业务语义与验收用例的挂载点（测试用例 AT-2751-* 与其 Realization 关系 1965），不宜删除。

### 2.2 SOLID 原则适用性（自研代码为零）

- 自研代码为零时，SRP/OCP/LSP/ISP 等面向对象设计原则**不直接适用**（无类/模块可供评审）。
- 在架构层面，方案体现了 DIP 精神的正向一面：业务能力（2748）依赖的是稳定的外部平台能力（GitHub Discussions），而非脆弱的自研实现，符合「依赖稳定抽象/平台」的方向。
- 风险：把能力整体委托给单一供应商（GitHub），形成**供应商锁定/单点依赖**。应在 2748 或 2752 的描述中显式记录「平台依赖边界」，为将来替换载体保留语义锚点。

### 2.3 安全性（子图 JSON 分享边界）——主要风险

- `export-to-kg.js` 导出的子图 JSON 是知识图谱快照，可能携带**敏感信息**：元素属性中的密钥/token、内部路径、commit 详情、个人或组织信息。通过公开 Gist / 仓库文件分享即等于公开泄露。
- 设计文档未定义**发布前脱敏控制**：无敏感信息扫描、无脱敏检查清单，这是当前方案最实质的缺口。
- 下载侧同样缺控制：导入前未要求校验子图 JSON 是否符合 `export-to-kg.js` 导出格式与大小上限，存在导入恶意/损坏数据的供应链风险。

### 2.4 性能 / 可用性

- 可用性与性能由 GitHub 平台（CDN、高可用、免运维）保证，符合 NF-1，正向成立。
- 需注意两个边界：① GitHub 平台中断时社区不可用（单点外部依赖，可接受但需记录）；② Gist 单文件存在大小上限（公开 Gist 单个文件约 10MB），大子图工作包需改用仓库文件承载，设计应明确大小分级策略。
- 工作包元数据无结构化索引，发现性完全依赖 GitHub 搜索，对「浏览/复用」体验有上限。

## 3. 修改建议（反馈给系统设计师 caoyang）

1. **补充发布安全控制**：在交付物「贡献指南 docs/developer-community-guide.md」中增加「发布前脱敏检查清单」（清理密钥/内部路径/个人信息），并在可选发布辅助脚本中内置敏感信息扫描与告警。
2. **补充下载格式校验**：明确 AC-4 的导入前置条件——子图 JSON 须通过 `export-to-kg.js` 导出格式校验与大小上限校验，避免导入恶意/损坏数据。
3. **记录平台依赖边界与大小策略**：在 2748/2752 描述中记录「载体为 GitHub Discussions、存在平台锁定」的依赖边界，并明确大于 Gist 上限的工作包改用仓库文件承载。
4. （建议）在 2751 工作包上新增一条安全验收用例（GIVEN 子图含敏感信息 / WHEN 发布 / THEN 被脱敏或拦截），使安全控制可外部验证。

以上第 1、2 点为必改项，第 3、4 点为建议项。
